# Android Network Privacy Monitor — V1 Master Specification

## 1. Project objective

Build a personal Android application that monitors network communications generated by applications installed on the device.

The primary purpose is to answer:

> Which applications communicate externally, with which destinations, how much data is exchanged, and which destinations are known analytics, advertising, or tracking services?

This is a **monitoring and privacy-analysis application**, not a packet inspection tool.

V1 MUST NOT decrypt TLS/HTTPS traffic and MUST NOT inspect application payload contents.

The application is for one personal device only and is not intended for public distribution.

---

# 2. Target environment

Target device:

- Samsung Galaxy A57 5G
- Android 16
- API level 36
- ARM64

Technical stack:

- Kotlin
- Native Android SDK
- Jetpack Compose
- Room
- SQLite

SDK requirements:

- `minSdk = 36`
- `targetSdk = 36`
- `compileSdk = 36`

No compatibility with Android 15 or earlier is required.

Do not introduce compatibility abstractions for older Android versions.

---

# 3. Core privacy principle

The application itself MUST respect the privacy it is designed to analyze.

All monitoring and analysis MUST happen locally on the Android device.

The application MUST NOT transmit:

- monitored domains;
- destination IP addresses;
- application usage information;
- installed application information;
- monitoring sessions;
- network statistics;
- classification queries;
- captured metadata

to an external service.

No analytics SDK or telemetry SDK should be included in V1.

Tracker classification databases must be available locally.

---

# 4. Scope of V1

V1 is primarily a **network monitoring application**.

It MUST support:

1. starting a monitoring session;
2. stopping a monitoring session;
3. monitoring all applications;
4. optionally monitoring only selected applications;
5. determining which Android application owns a network flow;
6. observing TCP and UDP communications;
7. supporting IPv4 and IPv6;
8. identifying remote IP addresses;
9. identifying remote ports;
10. identifying domain names when reasonably observable;
11. measuring bytes sent;
12. measuring bytes received;
13. counting connections;
14. classifying known destinations;
15. aggregating results;
16. storing completed monitoring sessions locally;
17. browsing previous sessions;
18. automatically controlling database size and retention.

V1 MUST NOT implement traffic blocking.

The architecture MUST, however, allow traffic blocking to be introduced cleanly in V2.

---

# 5. Explicitly out of scope for V1

Do NOT implement:

- TLS interception;
- HTTPS decryption;
- MITM certificates;
- payload inspection;
- packet-content storage;
- persistent packet capture;
- PCAP storage;
- firewall rules;
- domain blocking;
- application blocking;
- tracker blocking;
- remote synchronization;
- cloud services;
- user accounts;
- telemetry;
- remote analytics;
- timeline analysis;
- historical graphs of individual network events.

Do not implement these unless explicitly requested later.

---

# 6. Network architecture

Use Android `VpnService`.

The VPN is a **local monitoring VPN**.

There is no remote VPN server.

Conceptual architecture:

```text
Android applications
        |
        v
   Android VpnService
        |
        v
      TUN
        |
        +--------------------+
        |                    |
        v                    v
Monitoring pipeline    Forwarding engine
        |                    |
        v                    v
   Flow analysis           Internet
```

The application must continue to provide normal Internet connectivity while monitoring is active.

---

# 7. Forwarding engine

DO NOT implement a TCP/IP stack from scratch.

Use an existing, mature forwarding implementation compatible with:

- Android 16 / API 36;
- ARM64;
- TCP;
- UDP;
- IPv4;
- IPv6;
- Android `VpnService`.

Before selecting a forwarding dependency, verify:

1. license;
2. recent maintenance status;
3. Android 16 compatibility;
4. ARM64 compatibility;
5. TCP support;
6. UDP support;
7. IPv6 support.

The forwarding implementation MUST be isolated behind an abstraction:

```text
ForwardingEngine
```

The rest of the application must not depend directly on the selected forwarding library.

This is important because the forwarding implementation may be replaced later.

Do not select or integrate an obscure/unmaintained dependency merely because it is easy to use.

---

# 8. Application attribution

For each observed TCP/UDP connection, determine the Android application responsible for the connection.

Use modern Android APIs available on API 36, including where appropriate:

```text
ConnectivityManager.getConnectionOwnerUid(...)
```

Resolve:

```text
network flow
    ->
UID
    ->
package name
    ->
application information
```

Example:

```text
TCP connection
    ->
UID 10342
    ->
com.instagram.android
    ->
Instagram
```

Application attribution should happen when a flow is discovered.

It should NOT need to be recalculated for every packet.

Maintain an in-memory mapping between active flows and their application identity.

---

# 9. Application selection

Monitoring MUST support two modes.

### Global monitoring

Monitor all applications routed through the local VPN.

### Selected-app monitoring

Allow the user to select one or several installed applications.

Use Android VPN application filtering mechanisms where appropriate, such as:

```text
VpnService.Builder.addAllowedApplication(...)
```

The selected-app mode is particularly important because it allows focused analysis of one application without unrelated network noise.

---

# 10. Packet handling

Packets may be parsed in memory for monitoring purposes.

Support at minimum:

- IPv4;
- IPv6;
- TCP;
- UDP;
- DNS where observable.

Create a clear:

```text
PacketParser
```

component.

The parser should expose structured metadata to the rest of the application.

Raw packet contents MUST NOT be persisted.

---

# 11. Flow tracking

Create an in-memory:

```text
FlowTracker
```

A technical network flow may be identified using the appropriate tuple containing:

- protocol;
- local address;
- local port;
- remote address;
- remote port.

Track active flows sufficiently to calculate:

- application;
- destination;
- protocol;
- remote port;
- bytes sent;
- bytes received;
- connection lifecycle.

Technical flows exist primarily in memory.

They are NOT the main persistent unit.

---

# 12. Domain identification

Attempt to associate network destinations with domain names when reasonably possible.

Primary mechanism:

- observe DNS queries and responses visible to the VPN.

Maintain temporary mappings such as:

```text
graph.example.com
    ->
203.0.113.42
```

Domain information must include its provenance.

Example enum:

```text
DomainSource

DNS_OBSERVED
TLS_METADATA
UNKNOWN
```

If the domain cannot be determined reliably:

```text
domain = null
domainSource = UNKNOWN
```

Never fabricate a domain name.

Reverse DNS MUST NOT be presented as proof that an application contacted that hostname.

The application must gracefully handle encrypted DNS or other situations where the domain cannot be observed.

An IP-only destination is valid.

---

# 13. Destination classification

The application should help determine whether destinations are associated with privacy-sensitive services.

Use reputable local tracker datasets.

Initial sources:

- DuckDuckGo Tracker Radar;
- Disconnect tracker/service lists.

The classification system must be isolated behind:

```text
DestinationClassifier
```

Potential implementation components:

```text
DestinationClassifier
    |
    +-- TrackerRadarSource
    |
    +-- DisconnectSource
```

Datasets must be stored locally.

Do not query a remote classification API.

---

# 14. Classification categories

Keep the visible categories simple.

Use categories similar to:

```text
FUNCTIONAL
CDN
ANALYTICS
ADVERTISING
TRACKING
CRASH_REPORTING
UNKNOWN
```

Internally, multiple classifications may be retained if necessary.

Do not force every destination into a category.

When insufficient evidence exists:

```text
UNKNOWN
```

is the correct result.

---

# 15. Privacy classification

Separately represent whether a destination is known as a tracker.

Example:

```text
PrivacyClassification

KNOWN_TRACKER
POTENTIAL_TRACKER
UNCLASSIFIED
```

Do not equate analytics automatically with malicious behavior.

Do not claim that a company sells user information based solely on the network destination.

The application observes destinations and metadata, not the actual content or later use of transmitted data.

---

# 16. Classification evidence

Preserve the evidence supporting a classification.

Example:

```text
domain:
analytics.example.com

owner:
Example Corp

category:
ANALYTICS

privacyClassification:
KNOWN_TRACKER

sources:
TRACKER_RADAR
DISCONNECT

confidence:
HIGH
```

Suggested confidence system:

```text
HIGH
MEDIUM
UNKNOWN
```

General principle:

- HIGH: strong or corroborated classification;
- MEDIUM: classification provided by one reputable source;
- UNKNOWN: insufficient evidence.

Avoid presenting weak guesses as facts.

---

# 17. Persistent data model

Use Room over SQLite.

Do not persist raw packets.

The main persistent concepts should be approximately:

```text
MonitoringSession
ApplicationSummary
DestinationAggregate
DestinationInfo
```

The exact normalized Room schema may be chosen during implementation as long as it respects the behavior specified below.

---

# 18. Monitoring session

A session represents the period between pressing Start and Stop.

Conceptual model:

```text
MonitoringSession

id
startedAt
endedAt
status
monitoringMode
```

Possible status values:

```text
RUNNING
COMPLETED
FAILED
```

---

# 19. Persistent aggregation

Do NOT store every connection individually.

Aggregate network activity approximately by:

```text
Session
+ Application
+ Destination
+ Protocol
+ Remote port
```

Example:

Instead of storing:

```text
Instagram
TCP connection #1 -> example.com:443
14 KB sent

Instagram
TCP connection #2 -> example.com:443
8 KB sent
```

store:

```text
Instagram
example.com
TCP/443

connections = 2
bytesSent = 22 KB
bytesReceived = ...
```

This aggregation is fundamental to V1.

The application is designed to provide a **global picture**, not a packet or event timeline.

---

# 20. Destination aggregate

Conceptually store:

```text
DestinationAggregate

sessionId

applicationUid
packageName

remoteIp
domain
domainSource

protocol
remotePort

connectionCount

bytesSent
bytesReceived

classificationId
```

The final Room implementation may normalize repeated fields where appropriate.

---

# 21. No timeline

The user does NOT need to know whether:

```text
tracker.example
```

was contacted at 14:32 and again at 14:47.

Do not build a network-event timeline.

Do not persist individual connection timestamps solely for timeline reconstruction.

The relevant information is:

```text
Application X
contacted destination Y

N connections
X bytes sent
Y bytes received
classification Z
```

---

# 22. Storage limits

The application MUST enforce storage limits.

Defaults:

```text
maximum database/storage usage = 500 MB
maximum retention = 30 days
```

Configurable storage limits:

```text
100 MB
250 MB
500 MB
1 GB
2 GB
```

Configurable retention:

```text
7 days
30 days
90 days
unlimited
```

When a storage limit is exceeded:

1. delete the oldest completed sessions;
2. delete whole sessions rather than arbitrary rows where practical;
3. continue until usage returns below the configured limit.

Never delete the currently running monitoring session as part of automatic storage cleanup.

Provide:

```text
Storage used: X MB / Y MB
```

in settings.

Provide an:

```text
Erase history
```

action.

# 31. Summary statistics

For each application, calculate at minimum:

- total bytes sent;
- total bytes received;
- number of destinations;
- number of known tracker destinations;
- number of analytics destinations;
- number of advertising destinations;
- number of unknown destinations.

Also calculate traffic distribution where useful.


Do NOT convert this automatically into an arbitrary privacy score.

# 34. Performance principles

Packet processing is potentially high frequency.

Therefore:

- avoid unnecessary allocations in packet-processing loops;
- avoid database writes for every packet;
- maintain active counters in memory;
- batch or aggregate database updates;
- keep UI work away from packet-processing paths;
- do not perform expensive tracker-database searches for every packet;
- cache destination classifications;
- cache application UID resolution;
- cache DNS mappings appropriately.

Correctness comes before premature optimization, but obvious per-packet inefficiencies should be avoided.

---

# 35. Failure handling

Monitoring failures must not silently corrupt session data.

If monitoring terminates unexpectedly:

```text
session.status = FAILED
```

where possible.

The UI should indicate that the session did not complete normally.

Network forwarding failures must be surfaced clearly during development.

# 36. Required tests

Implement unit tests where appropriate for:

### Packet parsing

Verify:

- IPv4;
- IPv6;
- TCP;
- UDP;
- DNS parsing.

### Flow tracking

Verify:

- packets belonging to the same flow are associated correctly;
- different flows remain distinct;
- counters are correct.

### Application attribution

Verify:

```text
network flow -> UID -> package
```

where testable.

### Aggregation

Verify that two connections:

```text
same session
same application
same destination
same protocol
same remote port
```

are aggregated.

Verify that two different applications contacting the same destination remain separate.

### Classification

Verify known test domains against bundled datasets.

Verify unknown destinations remain:

```text
UNKNOWN
```

### Retention

Verify:

- sessions older than configured retention are removed;
- oldest sessions are removed when storage limits are exceeded;
- active session is not deleted.

### Database migrations

Room schema changes must use explicit migrations once persistent development data exists.

Do not rely on destructive migrations for normal upgrades.

# 37. Functional acceptance test

The following scenario MUST work before V1 is considered functional:

1. Install application on the Samsung Galaxy A57.
2. Open the application.
3. Select monitoring of one installed application.
4. Start monitoring.
5. Open and use the selected application for several minutes.
6. Return to Network Monitor.
7. Stop monitoring.
8. Open session results.

Expected result:

- monitored application is correctly identified;
- external destinations are visible;
- domain names appear when observable;
- IP addresses remain available;
- sent and received volumes are displayed;
- destinations are aggregated;
- known analytics/tracking services are classified;
- unknown services remain unknown;
- no payload contents are stored;
- Internet continued to function while monitoring was active.

# 38. Security and privacy acceptance requirements

V1 must satisfy:

**PRIV-01**

No monitored metadata is transmitted to an external server.

**PRIV-02**

No application payload is persisted.

**PRIV-03**

No TLS interception is performed.

**PRIV-04**

Tracker classification occurs locally.

**PRIV-05**

No third-party analytics/telemetry SDK is included.

**PRIV-06**

History can be deleted locally by the user.

# 39. Development strategy

Do NOT attempt to implement the complete application in one uncontrolled pass.

Development should proceed incrementally.

Recommended milestones:

### Milestone 1 — Project skeleton

Create:

- Android project;
- Kotlin;
- Compose;
- Room;
- architecture/package structure;
- basic navigation;
- placeholder screens.

No VPN implementation yet.

### Milestone 2 — Basic VpnService

Implement:

- VPN permission flow;
- foreground service;
- TUN creation;
- start/stop lifecycle.

Prove that the service works correctly.

### Milestone 3 — Forwarding

Integrate the selected forwarding engine.

Acceptance requirement:

> Internet works normally while VPN monitoring is active.

Do not continue until this is reliable.

### Milestone 4 — Packet parsing

Implement:

- IPv4;
- IPv6;
- TCP;
- UDP.

Expose structured flows.

### Milestone 5 — Application attribution

Implement:

```text
Flow -> UID -> application
```

Validate using known applications.

### Milestone 6 — DNS/domain resolution

Observe DNS where available.

Maintain temporary:

```text
domain <-> IP
```

information.

Handle unknown domains correctly.

### Milestone 7 — Flow aggregation

Implement in-memory flow tracking and persistent aggregated session results.

### Milestone 8 — Room persistence

Persist:

- sessions;
- applications;
- destination aggregates;
- classifications.

### Milestone 9 — Destination classification

Integrate local Tracker Radar and Disconnect datasets.

Add:

### Milestone 10 — Results UI

Implement:

- session overview;

### Milestone 11 — History and retention

Implement:

# 40. Codex operating instructions

Before implementing each milestone:

1. inspect the existing repository;
2. explain the intended changes;
3. identify files that will be created or modified;
4. identify relevant Android APIs/dependencies;
5. flag uncertainty before making major architectural changes.

Do not silently change the architecture defined by this specification.

If a technical requirement is impossible or inappropriate on Android 16, explain why and propose alternatives before changing it.

For third-party dependencies:

- verify maintenance;
- verify license;
- verify Android 16/API 36 compatibility;
- avoid unnecessary dependencies.

Prefer official Android APIs whenever practical.

Do not implement future V2 features unless necessary to maintain clean interfaces.

The first task is only:

> Do not write production code yet.

> 2. why it may be problematic;
